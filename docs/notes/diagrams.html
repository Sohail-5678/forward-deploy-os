ForwardDeploy OS, in pictures

ForwardDeploy OS takes messy vendor data, repairs it, checks it against purchase orders, and types the approved invoices into a 2009 web portal that has no API. Anything involving money that breaks a rule stops for a person, and every step is signed, hash-chained and replayable.

The real-world problem, and how it's solved

Integrations break in a few predictable places. Each one has a specific fix in the engine, not a general-purpose model doing its best.

What happens when a batch of invoices runs

Eight nodes run in order, and every node can stop the run. A checkpoint is taken after each one; the only place a person is required is the policy gate, and the run resumes from there.

How a changed export gets healed

Columns are matched by name and by what their values look like, then written down as a declarative spec rather than code. Two more columns were renamed and two kept their names; they map the same way.

How the agent works a portal that keeps changing

The agent reads a compact numbered map of the page instead of HTML. When a release moves a field, it finds it again by meaning, and asks a person when it is not sure.

Why a hidden instruction can't move money

Detection catches most attacks but can miss. What protects the money is code: models can only name fields, policy escalates unknown payees, and the guard checks every keystroke.

One engine, five places it runs

The same engine code powers the browser console, the guided demo, CI, Claude via MCP and the server. Any of them can run deterministically or with optional, validated LLM help.
